Bài tập: ủy quyền OAuth2 giữa Taxi và Wallet

Taxi muốn trừ tiền ví Wallet của Alice sau mỗi chuyến đi, kể cả khi Alice đã thoát app. Nhóm dựng cả ba ứng dụng: Wallet AS cấp token bằng Authorization Code + PKCE, refresh token và Client Credentials; Wallet API kiểm token và trừ tiền; Taxi liên kết ví và chạy job thanh toán. Trọng tâm là Wallet AS: AS phải kiểm những gì để code và token không rơi vào tay bên khác.

  • 65 phút thực hành
  • Trình bày sau phần thực hành

Bối cảnh

Wallet là dịch vụ giả định mô phỏng ví điện tử, không tái hiện API của ví thực nào. Alice là resource owner, Taxi là client, Wallet AS cấp token, Wallet API giữ số dư và trừ tiền. Taxi không được thấy mật khẩu ví của Alice và chỉ làm được những việc trong scope Alice đã đồng ý.

Nhóm dựng bốn thành phần bằng coding agent:

  • Wallet AS: user Alice và Bob với mật khẩu băm bằng argon2id hoặc bcrypt, trang login và trang consent, cặp khóa ES256 có kid tự sinh và nạp qua biến môi trường, route /.well-known/jwks.json, route /authorize và /token. Bảng clients, auth_codes, consents và refresh_tokens (hash, family_id, client_id, scope, expires_at, revoked_at, replaced_by). Dùng library cho JWT, băm và sinh số ngẫu nhiên; phần nhóm tự viết là logic giao thức.
  • Hai client đăng ký trong AS: taxi-web (confidential, secret lưu dạng hash, một redirect_uri, scope được phép wallet:read, wallet:charge, offline_access) và taxi-m2m (confidential, chỉ grant client_credentials, chỉ scope rates:read).
  • Wallet API: kiểm access token qua JWKS theo contract bên dưới. GET /wallet/balance cần wallet:read; POST /wallet/charges cần wallet:charge và principal_type=user; GET /public/rates cần rates:read. Có bộ đếm số lần trừ tiền và idempotency key tối giản (lưu key đã xử lý).
  • Taxi tối giản: nút liên kết ví, callback, session, kho refresh token phía server tách khỏi log, job thanh toán chạy khi Alice không có phiên và chỉ refresh tuần tự theo từng người dùng. Taxi dùng library OAuth client chuẩn (ví dụ openid-client cho Node.js hoặc Authlib cho Python) cho state và PKCE, không tự viết phần client của giao thức. Library chuẩn chạy được với AS của nhóm là một phép kiểm tra: AS đã nói đúng giao thức ở những phần library kiểm.
  • Script tấn công: gọi thẳng AS bằng HTTP cho từng trường hợp phải từ chối, in status và mã lỗi OAuth nhận được.

Contract access token: JWT ký ES256, iss là URL của Wallet AS, aud = wallet-api, có sub, client_id, scope, exp sau 120 giây và principal_type = user hoặc client. Cấu hình lab: code sống 60 giây, access token 120 giây, refresh token 7 ngày. AS của bài tập chỉ dùng trong lab; production dùng AS đã được kiểm chứng như Keycloak.

Mục tiêu

Dựng khung và baseline

Dựng Wallet AS với user, client, khóa và JWKS; Wallet API kiểm token theo contract; Taxi tối giản; script tấn công. Chạy script tấn công lần đầu khi AS chưa có các kiểm tra bên dưới và ghi kết quả, để so với kết quả sau khi hiện thực.

Endpoint /authorize

client_id phải đã đăng ký và redirect_uri phải khớp chính xác chuỗi đã đăng ký; sai thì AS hiện lỗi tại trang của mình và không redirect, vì redirect tới URI lạ là gửi code cho người khác. Scope phải nằm trong danh sách được phép của client, và request phải có code_challenge với method S256; sai thì redirect về client với invalid_scope hoặc invalid_request. Alice đăng nhập và xem consent trên trang của AS; từ chối thì redirect với access_denied. Đồng ý thì AS lưu consent, sinh code ngẫu nhiên, lưu hash của code cùng client, redirect_uri, user, scope và code_challenge. Mọi redirect về client mang lại nguyên giá trị state.

Đổi code lấy token

/token xác thực client bằng HTTP Basic và so với secret đã băm; sai thì 401 invalid_client. Với grant_type=authorization_code, code phải tồn tại, chưa dùng, còn hạn, cấp cho đúng client, redirect_uri trùng với lúc authorize và SHA-256(code_verifier) khớp challenge; sai thì 400 invalid_grant. Đánh dấu code đã dùng trong cùng transaction với lúc phát token, để hai request đồng thời không cùng đổi được một code. Code bị dùng lại thì từ chối và thu hồi token đã cấp từ code đó (RFC 6749 mục 4.1.2). AS phát access token theo contract, và chỉ phát refresh token khi scope có offline_access. Kết quả quan sát được: Taxi liên kết ví và đọc được số dư.

Refresh và thanh toán

Refresh token là chuỗi ngẫu nhiên, không phải JWT; DB chỉ lưu hash. Mỗi lần refresh cấp cặp token mới và đánh dấu token cũ đã dùng; token đã dùng xuất hiện lại thì thu hồi cả family. AS còn kiểm: refresh token cấp cho đúng client đang xác thực, consent chưa bị gỡ, scope yêu cầu không rộng hơn lúc Alice đồng ý. Job thanh toán của Taxi chạy khi Alice không có phiên và access token đã hết hạn: refresh thành công, tiền bị trừ đúng một lần theo bộ đếm của Wallet API.

Gỡ quyền

Phần mở rộng. Trang tài khoản của AS cho Alice gỡ quyền của Taxi: đặt revoked_at cho consent và thu hồi các refresh family của cặp Alice và Taxi. Lần refresh tiếp theo của Taxi nhận invalid_grant, Taxi chuyển sang trạng thái chưa liên kết. Nhóm ghi policy cho access token còn hạn: Wallet API kiểm offline nên token còn được nhận tới exp.

Client Credentials

Phần mở rộng. Chỉ client được phép dùng grant này mới nhận token, scope phải trong danh sách của client. Token có sub là client_id, principal_type=client và không kèm refresh token. Kết quả quan sát được: taxi-m2m gọi được GET /public/rates; xin wallet:charge thì nhận invalid_scope; dùng token này gọi POST /wallet/charges thì nhận 403.

Bảng grant

Ghi response của token endpoint do nhóm viết cho từng grant đã hiện thực: có hay không refresh_token, giá trị sub, aud, scope, principal_type, expires_in. Đối chiếu từng trường với RFC 6749 mục 5.1. Bảng điền từ response đã quan sát, không chép từ slide.

Tiêu chí đạt. Taxi liên kết ví qua trang consent của AS, trình duyệt không thấy token, và đọc được số dư. Job thanh toán refresh được khi Alice không có phiên và trừ tiền đúng một lần. Script tấn công cho redirect_uri không đăng ký, thiếu code_challenge, code dùng lại, code hết hạn, code_verifier sai, client secret sai, đổi code bằng client khác, replay refresh token cũ và refresh bằng client khác đều bị từ chối với đúng mã lỗi. Kết quả nộp là kết quả chạy thật, kể cả kết quả chưa đạt.

Cách làm

  1. Làm rõ với agent. Đề bài chỉ nêu mục tiêu. Nhóm brainstorm với agent để chốt cấu trúc repo cho ba ứng dụng, contract access token, danh sách kiểm tra ở /authorize và /token, thứ tự kiểm, mã lỗi OAuth cho từng trường hợp, trường hợp nào hiện lỗi tại AS và trường hợp nào redirect về client, transaction khi đổi code, cách lưu và xoay refresh token, danh sách script tấn công. Ghi các quyết định vào plan trước khi viết code. Không đưa secret, private key, code hay token vào prompt của agent.
  2. Hiện thực theo luồng inspect, plan, implement, run, test, verify. Thứ tự gợi ý: dựng khung và script tấn công, /authorize, /token đổi code, refresh và job thanh toán, chạy lại script tấn công, gỡ quyền, Client Credentials.
  3. Tự kiểm soát. Nhóm đọc diff, giải thích log và bảo vệ quyết định. Câu trả lời của agent không dùng làm evidence.

Sản phẩm nộp

  • Repo có README để chạy lại toàn bộ: cách sinh khóa, khởi động Wallet AS, Wallet API, Taxi và chạy script tấn công.
  • Plan gồm các quyết định đã chốt với agent, viết trước khi hiện thực.
  • Mã nguồn ba ứng dụng và script tấn công, kèm library và phiên bản đã dùng.
  • Bảng kiểm tra của AS: mỗi kiểm tra ở endpoint nào, sai thì trả gì, chặn tấn công nào.
  • Output script tấn công trước và sau khi hiện thực.
  • Trace redirect của lần liên kết ví, đã che code và token.
  • Log job thanh toán kèm mốc exp và bộ đếm trừ tiền của Wallet API.
  • Bảng grant điền từ response của AS.
  • Policy thu hồi, gồm hành vi của access token còn hạn sau khi Alice gỡ quyền.
  • Ghi chú trade-off và giới hạn của AS lab so với AS dùng trong production.
Không nộp secret, private key, authorization code, access token, refresh token hay session cookie nguyên giá trị; dùng nhãn kèm mốc thời gian. Dùng dữ liệu giả.
