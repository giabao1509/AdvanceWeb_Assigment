1. Tổng quan và stack cuối cùng

Nhóm xây dựng sáu endpoint cho Product và Cart, tập trung vào đặc tả API rõ ràng, kiểm tra dữ liệu trước khi truy cập database, định dạng lỗi thống nhất và log JSON dễ tra cứu. Toàn bộ công nghệ dưới đây là quyết định chủ động của nhóm.

2. Node.js và Express.js

Node.js phù hợp REST API thiên về I/O. Express có middleware model rõ, tích hợp trực tiếp với Pino, Swagger UI và OpenAPI validator. Hàm createApp({ repository, logger }) cũng cho phép dependency injection trong test mà không cần DI framework.

Phương án không chọn

  • Spring Boot: enterprise tooling tốt nhưng nhóm ưu tiên JavaScript xuyên suốt và ít boilerplate hơn.
  • NestJS: module/DI mạnh nhưng thêm abstraction chưa cần cho API nhỏ.
  • Fastify: hiệu năng tốt, nhưng nhóm ưu tiên hệ sinh thái middleware quen thuộc của Express; framework throughput chưa phải nút thắt.
  • Node http thuần: giảm dependency nhưng phải tự xây routing, middleware và error pipeline.
Điểm đánh đổi: Express không quy định sẵn kiến trúc, nên nhóm phải chủ động tách route, service, repository, error và các thành phần hạ tầng.

3. Contract-first, Swagger UI và validation

openapi.yaml là nguồn duy nhất cho tài liệu tại /docs, kiểm tra request và kiểm tra response. Nhờ đó tài liệu và API thực tế không phải duy trì hai schema độc lập.

Validator không coerce kiểu, không xóa field lạ và không cho query parameter ngoài contract. Vì middleware chạy trước routes, request sai không thể chạm service, repository hoặc Prisma.

Phương án không chọn

  • Markdown thủ công: không machine-readable và dễ lệch implementation.
  • Postman làm nguồn chính: hữu ích cho demo nhưng sẽ trở thành contract thứ hai.
  • Code-first annotations: làm schema phụ thuộc code, trái mục tiêu contract-first.
  • Joi/Zod song song: tạo thêm một schema validation cần đồng bộ với OpenAPI.

4. PostgreSQL và Prisma

Quan hệ Product-Cart-CartItem cần foreign key, unique/composite key, check constraint và transaction. PostgreSQL phù hợp hơn document database cho mô hình này. Prisma cung cấp schema mapping, migration, generated client, seed/reset và transaction API.

  • Giá luôn đọc từ database, không tin giá client gửi.
  • Tiền được lưu và tính bằng integer cents.
  • Composite key ngăn trùng sản phẩm trong một cart.
  • Mutation chạy trong transaction.

Phương án không chọn

MongoDB không tận dụng tốt relational constraints; raw SQL làm tăng mapping/transaction boilerplate; SQLite khác môi trường PostgreSQL đích; Sequelize và TypeORM dùng được nhưng nhóm đánh giá Prisma có schema và migration workflow gọn hơn.

Seed dùng UUID, SKU, giá, stock và trạng thái cố định. Mỗi lần reset database đều tạo lại cùng dữ liệu đầu vào, nên acceptance tests không phụ thuộc dữ liệu do test trước để lại.

5. Error contract và request ID

Mọi lỗi có bốn field ổn định: code, message, details và request_id. AppError biểu diễn lỗi ứng dụng; cartErrors tạo lỗi nghiệp vụ; middleware trung tâm chuyển validator/domain/unexpected errors về cùng format.

{
  "code": "VALIDATION_ERROR",
  "message": "Request is invalid",
  "details": [],
  "request_id": "7f3c2a9e-..."
}

Cùng UUID xuất hiện trong X-Request-Id, error body và log. Client không nhận stack trace, SQL hoặc secret.

6. Logging: Pino thay vì ELK trong phạm vi hiện tại

Pino và pino-http tạo log JSON có method, URL, status, thời gian xử lý và request ID. Authorization, cookie, password, token và secret được che trước khi ghi. Ứng dụng ghi log ra stdout; Docker lưu lại, giới hạn dung lượng và tự xoay vòng các file log phía dưới.

logging:
  driver: local
  options:
    max-size: "10m"
    max-file: "5"

Cấu hình giới hạn khoảng 50 MB log/container trước compression, tránh api.log tăng vô hạn và tránh lưu trùng.

Phương án không chọn

  • console.log: chỉ ghi nội dung ra stdout và không tự cung cấp cơ chế lưu trữ. Khi chạy Node trực tiếp, log chỉ hiện trên terminal và không còn để tra cứu sau khi đóng terminal nếu không chuyển output sang file hoặc hệ thống thu thập log. Trong Docker, stdout vẫn có thể được lưu lại, nhưng các dòng console.log thường thiếu level, request ID, định dạng thống nhất và cơ chế che dữ liệu nhạy cảm, nên khó xác định request gây lỗi và khó điều tra sự cố.
  • Morgan: access log tốt nhưng không đủ cho application/domain errors.
  • Winston: nhiều transport nhưng cấu hình nặng hơn nhu cầu JSON logging hiện tại.
  • ELK: search/dashboard mạnh nhưng tốn tài nguyên và công vận hành cho một service nhỏ.

Việc giữ stdout JSON cho phép bổ sung ELK, Loki hoặc cloud logging sau này mà không sửa business layer.

7. Docker và migration lifecycle

Dockerfile nhiều giai đoạn sinh Prisma Client trong bước build, chỉ giữ dependency cần thiết trong image chạy API và sử dụng user không phải root. Compose xác định thứ tự:

postgres --healthy--> migrate --completed successfully--> api

migrate là one-shot service chạy prisma migrate deploy. API chỉ bắt đầu khi database có schema hợp lệ. Seed là thao tác chủ động, không tự chạy ở mỗi production startup.

Điểm đánh đổi: Docker làm lần build đầu tiên lâu hơn. Với hệ thống production lớn, migration nên chạy như một job trong CI/CD; service chạy một lần trong Compose phù hợp local và demo.

Chiều phụ thuộc

route → service → repository → Prisma → PostgreSQL

Route biết service, nhưng service không biết Express route. Service sử dụng repository, còn repository không biết HTTP status hay response header. app.js là nơi tạo và nối các thành phần. Logging, request ID, OpenAPI validation và error handling được đặt trong middleware pipeline để không phải lặp lại ở từng endpoint.

12. Demo `/docs`, response và log

Mở http://localhost:3000/docs, chọn POST /carts/{cartId}/items, bấm Try it out, dùng cart ID 20000000-0000-4000-8000-000000000002 và body:

{
  "product_id": "10000000-0000-4000-8000-000000000001",
  "quantity": 11

Swagger UI phải hiển thị status 400, header X-Request-Id và error body có cùng request_id. Sau đó tìm ID trong log:

docker compose logs api | Select-String '<request-id>'

13. Hạn chế, hướng mở rộng và kết luận

Authentication, checkout, payment, reservation, distributed tracing, centralized logging, rate limiting, cache, secrets manager và horizontal database scaling nằm ngoài phạm vi hiện tại.

Nếu hệ thống mở rộng, bước tiếp theo là log aggregation, trace ID xuyên service, secret management, migration trong CI/CD và concurrency strategy cho inventory.

Kết luận: toàn bộ công nghệ là lựa chọn của nhóm. Kết quả cuối ưu tiên việc API tuân thủ đúng đặc tả, dễ cài đặt và chạy lại theo cùng một quy trình, đồng thời phù hợp với quy mô hiện tại. Spring Boot, NestJS hay ELK đều là giải pháp tốt, nhưng nhóm đánh giá chi phí triển khai và vận hành của chúng chưa cần thiết cho API này.
