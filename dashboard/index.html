1 · Problem

Một luồng đặt hàng, hai boundary, hai nhóm consumer khác nhau

Người dùng gọi POST /orders với sku và quantity. Order API xin Inventory giữ hàng: đủ hàng thì tạo order, thiếu hàng thì trả lỗi nghiệp vụ. Bài toán: chuyển chặng nội bộ từ REST sang gRPC mà không ai bên ngoài nhận ra.

BOUNDARY NGOÀI Browser → Order API

  • Consumer là browser và bên thứ ba. Nhóm không quyết định khi nào họ cập nhật.
  • URL, status code và body phải giữ nguyên trước và sau khi đổi transport, ở cả đường đủ hàng lẫn thiếu hàng.
  • Lỗi nghiệp vụ không được biến thành HTTP 500 tùy tiện.

BOUNDARY TRONG Order API → Inventory

  • Nhóm viết cả hai đầu nhưng deploy từng service riêng.
  • Vì vậy client cũ có thể chạy với server mới, và ngược lại.
  • Khi Inventory chậm hoặc chết, Order API phải trả lời trong thời gian hữu hạn.

Deadline · field vắng · client cũ

  • ⏱
    Deadline 2000 ms cho cả REST (AbortSignal.timeout) lẫn gRPC (deadline). Khi bật chế độ chậm, Inventory ngủ 5 s.
  • ∅
    Không giữ hàng ma: Inventory kiểm tra call.cancelled hoặc socket đã đóng trước khi trừ tồn.
  • ?
    Field vắng: Timestamp là message nên có presence. Khi vắng, Order API v2 bỏ key reservationExpiresAt, không suy ra 1970-01-01.
  • #
    Client cũ: bundle esbuild được đóng băng trước khi thêm field. Lúc chạy, client log sha256 và gửi metadata x-client-version để Inventory log lại.
  • ⚖
    Đo payload bằng 2 đại lượng tách riêng: message đã serialize và wire bytes (qua TCP proxy).

5 · Trade-off

Được gì, mất gì, và phép đo nói được tới đâu

Các con số dưới đây lấy trực tiếp từ evidence/payload.json (đo lúc …).

gRPC được

  • Message request B so với JSON B.
  • Wire bytes mỗi lời gọi ấm (đủ hàng): B so với REST B. HPACK nén các header lặp lại.
  • Contract có kiểu. Thay đổi schema hiện ra thành lỗi compile (TS2741) chứ không phải lỗi runtime.
  • Deadline truyền sang server (grpc-timeout), server biết caller đã bỏ đi.
  • Thêm field tương thích hai chiều: client cũ bỏ qua tag lạ, client mới thấy field vắng.

chi phí mất

  • Toolchain sinh code: gặp 3 lỗi trên Windows (đường dẫn có dấu cách, plugin .cmd, thiếu well-known types).
  • Payload nhị phân: không curl hay DevTools được, phải tự log grpcCode, details và trailer.
  • Chi tiết thiếu hàng nằm trong trailer, dễ bị bỏ sót nếu không chủ động đọc.
  • Mỗi thay đổi schema phải sinh lại code ở cả hai repo và giữ kỷ luật về tag và package.
  • Client cũ bỏ qua field mới trong im lặng, không có cảnh báo nào.
  • Browser vẫn cần REST/JSON (không làm gRPC-Web), nên Order API phải duy trì hai kiểu contract.

giới hạn của phép đo

  • Loopback, cùng một máy, không TLS, N = lần mỗi case.
  • Latency nội bộ: REST ms và gRPC ms (median). End-to-end: và ms. Trên loopback cả hai đều chỉ vài ms; với N nhỏ như vậy, phép đo không đủ để kết luận transport nào nhanh hơn trong môi trường thật.
  • Wire bytes không gồm TCP/IP header hay bắt tay TCP. HPACK phụ thuộc trạng thái kết nối.
  • Lỗi gRPC có message 0 B (thông tin nằm trong trailer), nên bảng message không phản ánh đúng kích thước lỗi; phải xem thêm bảng wire.
  • REST bị phình vì header mặc định của Express (X-Powered-By, ETag…). Có thể cắt bớt, nhưng nhóm giữ nguyên để đo trung thực.
